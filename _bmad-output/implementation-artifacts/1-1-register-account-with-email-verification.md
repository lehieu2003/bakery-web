# Story 1.1: Register Account with Email Verification

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a visitor,
I want to create an account and verify my email,
so that I can access member features securely.

## Acceptance Criteria

1. Given I am a new visitor with a valid email, when I submit registration data, then the system creates a pending account and sends a verification email.
2. Given a pending account, when email verification is not completed, then authenticated routes are blocked for that account.
3. Given duplicated email or invalid payload, when registration is attempted, then API returns standardized error envelope without leaking sensitive details.
4. Given verification token is valid, when user confirms email, then account status transitions to verified and login flow can proceed.

## Dev Notes

- Story source from epic context:
  - Epic 1 objective: secure customer identity foundation (FR1-FR5).
  - This story directly covers FR1 and enables FR2-FR5.
- Required architecture constraints for this story:
  - Preserve route -> service -> data-access layering.
  - Keep API envelope shape exactly `{ success, data?, error? }`.
  - Use existing stack only (Next.js App Router, React, TypeScript, Prisma, PostgreSQL).
  - Keep secrets/integration credentials in environment variables only.
  - Add structured logs for operational visibility.
- Security and reliability guardrails:
  - No account enumeration in error responses.
  - Enforce TLS/session handling via existing auth/session utilities.
  - Verification token must have expiration and one-time usage semantics.

### Project Structure Notes

- Expected server-side touch points:
  - `app/api/auth/**/route.ts` for route handlers.
  - `services/auth.service.ts` for auth orchestration.
  - `lib/session.ts` for session/authorization checks.
  - `lib/prisma.ts` and `prisma/schema.prisma` for persistence.
  - `types/api.types.ts` for stable response typing.
- Keep boundaries intact:
  - No direct DB access from UI components/hooks.
  - No custom response shapes per endpoint.
